# Q App Feedback Implementation Plan

Purpose: Implement the following UX/product feedback into the Q / Quirkle Companion app repo. This plan is optimized for Codex: clear scope, implementation order, likely touchpoints, and acceptance criteria.

Working assumptions:
- The app is a front-end-first web app.
- Game state is already tracked locally.
- There are existing screens/routes or view states for: Choose Players, Player Names, Main Game, Final, and Main/Start Menu.
- The “Q” button/logo already exists somewhere in the app chrome/header.
- Preserve current app style, but improve clarity, polish, and phone usability.

Core implementation principle:
Prefer small, contained changes. Avoid large rewrites unless the current structure makes a feature impossible. Keep state transitions explicit and testable.

---

## 2. Screen: Player Names

### Request
Default to capitalizing the first letter when entering player names.

### Implementation Notes
- Locate the player name input handling logic.
- Capitalize the first alphabetical character of the entered name.
- Preserve the rest of the user’s input unless there is already an app-wide formatting convention.
- Do not fight the user too aggressively. If they manually change later letters, preserve that.
- Suggested helper:

```js
function capitalizeFirstLetter(value) {
  if (!value) return value;
  return value.charAt(0).toUpperCase() + value.slice(1);
}
```

- Apply on input change or blur. Prefer on input change only if it does not create cursor-position bugs. If cursor handling becomes awkward, apply on blur and before saving/continuing.

### Acceptance Criteria
- Typing “scott” results in “Scott” by default.
- Existing names still load correctly.
- Empty strings do not error.
- User can still enter custom names without weird input jumps.

## 3. Screen: Main Game — Button Press Polish

### Request
Add slight animation for button presses.

### Implementation Notes
- Apply to score buttons, numpad buttons, Enter, Quirkle buttons, Last Tile, Undo, and other primary game action buttons.
- Keep the animation subtle and fast.
- Prefer CSS-only interaction states:
  - `:active { transform: scale(0.96); }`
  - short transition: `transform 80ms ease`, maybe `filter` or `box-shadow`
- Do not make the UI feel slow.
- Respect reduced motion if the app already supports it, or add a minimal reduced-motion guard.

### Acceptance Criteria
- Pressing/tapping buttons gives immediate visual feedback.
- Animation feels responsive on phone.
- No layout shift.
- Reduced-motion users are not forced into heavy animation.

## 4. Screen: Main Game — Haptic Feedback

### Request
Add haptic feedback on button press, with a menu option to turn haptics off.

### Implementation Notes
- Use the browser Vibration API where available:

```js
if (hapticsEnabled && 'vibrate' in navigator) {
  navigator.vibrate(10);
}
```

- Haptics should fire only for intentional button actions, not every render/state update.
- Add a user-facing setting/toggle in the app menu/settings area.
- Persist the setting in localStorage.
- Default: haptics ON may be okay for a mobile scoring app, but consider defaulting ON only if not annoying. If uncertain, default ON and make the toggle easy to find.
- Gracefully do nothing on devices/browsers that do not support vibration.

### Suggested helper

```js
const HAPTICS_STORAGE_KEY = 'qApp.hapticsEnabled';

function triggerHaptic(enabled) {
  if (!enabled) return;
  if (typeof navigator !== 'undefined' && 'vibrate' in navigator) {
    navigator.vibrate(10);
  }
}
```

### Acceptance Criteria
- Supported mobile devices vibrate subtly on button presses.
- User can turn haptics off.
- Haptic preference persists after refresh.
- App does not error in desktop browsers or unsupported mobile browsers.

## 5. Screen: Main Game — Header Mini Score Bar Preview

### Request
On the Header Mini Score Bar, see if there is enough space to show:

`current score + current active number pressed`

Example:

`17 +6`

Purpose: Make it easy to see what score is about to be submitted for the active player.

### Implementation Notes
- Locate the header mini score bar / player score summary component.
- Identify the active player and the currently buffered score input.
- For the active player only, display a pending score preview when there is a non-empty active input.
- Example display logic:
  - inactive player: `Scott 17`
  - active player with pending input 6: `Scott 17 +6`
  - active player with no pending input: `Scott 17`
- Avoid crowding. If space is tight, use compact formatting:
  - `17+6`
  - or show pending value in a small badge.
- Do not include submitted score until Enter is pressed.

### Acceptance Criteria
- Active player’s pending score is visible before submission.
- The preview updates as numpad input changes.
- The preview clears after Enter/submission.
- Layout remains readable for 2, 3, and 4 players on phone.
- Inactive players are not confusingly shown with pending values.

## 6. Screen: Main Game — Quick Undo Last Entry

### Request
Add “Undo Last Entry.” It should:
- Decrement the active player to the previous player.
- Remove the most recently added score entry.
- Remove that score from the player’s total.
- Allow immediate reentry.
- Support roughly 3–5 undo levels total.
- Expected use is only recent mistake correction.
- Do not mark quick undo corrections as edited/tampered.

### Implementation Notes
- This should operate on submitted turn entries, not on the current unsubmitted score buffer.
- Add a bounded history stack of recent submitted scoring actions.
- Each submitted turn should produce an entry with enough info to undo:
  - playerId / playerIndex
  - score value submitted
  - turn/round index if applicable
  - previous active player index
  - next active player index
  - whether special buttons were involved, if relevant
  - timestamp optional
- Keep only the most recent 3–5 entries. Suggested: 5.
- Undo should reverse the latest submitted score and restore active player to that player.
- If the score sheet is represented as rows/turns, remove the latest score cell/entry cleanly.
- If the latest entry was manually edited after submission, decide carefully:
  - simplest: undo removes the latest entry as currently stored.
  - do not add tamper marker for undo itself.
- Disable or hide Undo when there is nothing to undo.

### Suggested model

```js
const MAX_UNDO_HISTORY = 5;

const submittedAction = {
  id: crypto.randomUUID?.() ?? String(Date.now()),
  playerIndex,
  score,
  previousTotal,
  nextTotal,
  previousActivePlayerIndex,
  nextActivePlayerIndex,
  scoreEntryId,
};
```

### Suggested behavior
- On score submit:
  1. Save current player total as `previousTotal`.
  2. Add score to score sheet.
  3. Save new total as `nextTotal`.
  4. Push action into undo history.
  5. Trim undo history to latest 5.
  6. Advance active player.

- On undo:
  1. Pop latest action.
  2. Remove that score entry from score sheet.
  3. Restore that player’s total to `previousTotal`, or recompute totals from score sheet.
  4. Set active player to `playerIndex` / `previousActivePlayerIndex` as appropriate.
  5. Clear current pending input.

### Acceptance Criteria
- User can undo the most recent submitted score.
- Active player returns to the player whose score was undone.
- Total score decrements correctly.
- Score sheet removes the undone entry.
- Up to 5 recent entries can be undone.
- Undo button disabled/hidden when no undo is available.
- Quick undo does not create the manual-edit/tamper indicator.

## 7. Screen: Main Game — Manual Score Sheet Editing

### Request
Allow clicking/tapping a score sheet cell to manually edit that number for fixing scores.

Also add an indicator, like an asterisk, to show the score was adjusted/tampered with.

Important: Do not show this indicator for quick undo corrections.

### Implementation Notes
- Locate score sheet rendering.
- Make score cells interactive.
- On tap/click, open an inline editor, small modal, popover, or prompt-style controlled input.
- Prefer a small modal or inline edit field that works well on mobile.
- User should be able to change the score value and save/cancel.
- Validate input:
  - integer
  - likely >= 0
  - allow app’s existing scoring rules
- When a cell is manually edited:
  - update that entry’s value
  - mark that entry as manuallyEdited: true
  - update affected player total
- Strongly prefer recomputing totals from score entries after edits to avoid drift.
- Display an indicator near the adjusted score:
  - `*`
  - or small “edited” dot/badge
- Consider a subtle legend somewhere: `* edited score`
- Do not mark entries as edited due to Undo.

### Suggested data structure update

```js
const scoreEntry = {
  id,
  playerIndex,
  value,
  manuallyEdited: false,
  originalValue: null,
  createdAt,
  editedAt: null,
};
```

On manual edit:

```js
{
  ...entry,
  value: newValue,
  manuallyEdited: true,
  originalValue: entry.originalValue ?? entry.value,
  editedAt: Date.now(),
}
```

### Acceptance Criteria
- User can tap/click an existing score cell and edit it.
- Save updates the score sheet and total.
- Cancel leaves score unchanged.
- Edited cells show a visible indicator.
- Indicator does not appear for normal submissions.
- Indicator does not appear simply because of quick undo.
- Editing works on mobile.

### Acceptance Criteria
- User can edit final game name.
- Date remains visible even after the name changes.
- Edited name persists in game history/archive if applicable.

## 10. General Visual Pass — Text Contrast

### Request
The text for “Royale” and some other text can blend into the background. Do another pass to ensure any text, especially text without a card background, has enough contrast to be easily readable.

### Implementation Notes
- Audit text that sits directly on gradient/image/color backgrounds.
- Prioritize:
  - Royale text
  - screen titles
  - labels without card backgrounds
  - secondary text over decorative backgrounds
  - buttons with transparent/ghost styles
- Fix with one or more of:
  - stronger text color
  - text shadow
  - subtle overlay/scrim behind text
  - card/chip background
  - increased font weight
  - adjusted background gradient
- Do not flatten the app’s personality. Preserve style while improving readability.
- Target WCAG-ish contrast, especially on mobile outdoors.

### Acceptance Criteria
- “Royale” text is clearly readable.
- Text without card backgrounds has sufficient contrast.
- No important labels disappear into the background.
- Visual style still feels like the existing Q app.

# Edge Cases

- Undo when no score has been submitted.
- Undo after a manual edit.
- Manual edit after several turns.
- Manual edit to 0.
- Manual edit to empty or invalid value.
- Player names with one character.
- Player names pasted in instead of typed.
- Haptics on unsupported browser.
- 2-player, 3-player, and 4-player layouts.
- Header Mini Score Bar with long player names.
- Returning to Main Menu during an active game.
